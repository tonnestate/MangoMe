# MangoMe v0.3.17 — KeyFile-Safe Zero-Touch LOCAL_HOST

## Root cause

v0.3.16 stopped on the managed host because `/etc/mongod.conf` contains `security.keyFile`. The release classified every keyFile configuration as an unsupported cluster/transition security model, so setup could not complete even though the live MongoDB listener was loopback-only.

## Repair

v0.3.17 distinguishes MongoDB client authorization from internal member authentication.

- Without `security.keyFile`, zero-touch uses `security.authorization: disabled`.
- With `security.keyFile`, zero-touch preserves the keyFile and existing replication/member-authentication settings and sets `security.transitionToAuth: true`.
- The service configuration is backed up before modification and `mongod.service` is restarted once.
- The live listener must be loopback-only before and after the restart.
- Anonymous ping/database visibility/index readiness must succeed before obsolete MangoMe credential artifacts are deleted.

MongoDB documents `transitionToAuth` as accepting authenticated and unauthenticated connections and not enforcing user access controls while an internal authentication mechanism such as `security.keyFile` remains configured. That matches MangoMe's explicitly chosen LOCAL_HOST trust model without deleting cluster/member authentication material.

## Still fail-closed

Zero-touch still stops for:

- any non-loopback MongoDB listener;
- non-root host migration;
- command-line `--auth`, `--keyFile`, or `--clusterAuthMode` that would require rewriting service arguments;
- ambiguous/duplicate security configuration;
- cluster/X.509 security without a keyFile where a safe automatic transition is not proven;
- legacy database selection such as `mangome_uai_eval`.

No database adoption, repair, migration, keyFile deletion, dbPath change, firewall change, or non-MangoMe database mutation is authorized by this repair.
