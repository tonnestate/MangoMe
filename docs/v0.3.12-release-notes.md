# MangoMe v0.3.12 — v0.3.11 Repair & External Enforcement Boundary

Release date: 2026-09-29

v0.3.12 repairs the concrete regressions found after v0.3.11 and tightens the boundary between MangoMe governance and physical runtime enforcement. It deliberately does not introduce cryptographic key management.

## Worker facade repair

- Keeps exactly seven normal worker MCP tools.
- Restores semantic routing for all 100 pre-existing advanced v0.3.11 capabilities.
- Restores the 46 capabilities that v0.3.11 accidentally made unreachable from the normal worker path.
- Keeps the advanced/internal MCP endpoint available explicitly rather than expanding the normal surface again.
- Preserves weak-agent guidance: `disposition`, `recommended_next_action`, `allowed_next_actions`, `forbidden_next_actions`, and `reason_codes`.

## Structural repair

- Prefers `tree-sitter-language-pack.get_parser(...)` where available.
- Adapts str/bytes parser input and `type`/`kind`, byte-range and position differences.
- Retains the standalone Tree-sitter fallback where interoperable.
- Retains bounded text fallback and non-blocking `STRUCTURAL_CONTEXT_UNAVAILABLE` behavior.
- Corrects architecture wording: PCH/1 and SRA/1 remain authoritative for their own persisted/deterministic state; structural projections are advisory data beside them.

## External enforcement boundary

MangoMe does not become an OS sandbox. A host/router may apply an external enforcement backend after MangoMe authorizes delegation. The worker cannot widen that host policy.

Enforcement provenance can use the existing `record_execution_receipt(..., metadata=...)` field with keys such as:

- `enforcement_backend`
- `enforcement_version`
- `policy_ref`
- `policy_digest`
- `audit_ref`
- `enforcement_decision`

These values are provenance/observations, not truth or assurance. Independent material claims still flow through existing Evidence and AV/1 semantics.

## Explicit non-goals

v0.3.12 does not add HMAC, key files, key rotation, a cryptographic mutation journal, blockchain/consensus, a new Mongo schema, `nono`, OpenShell, LlamaFirewall, Inspect AI, NeMo Guardrails, or a second governance layer. External components are evaluated outside the MangoMe runtime first.

## Evaluation freeze

The evaluation baseline removes the temporary worker-CLI monkeypatch. Managed configuration now selects its MCP surface explicitly: `worker` is the safe default for direct/programmatic setup, while the advanced CLI selects `advanced` deliberately.

A lightweight `tools/release_smoke.py` gate verifies the installed package with the in-memory backend: exactly seven normal worker tools, complete routing of the advanced capability surface, and a real in-process read-only MCP health call. `make check` includes this gate.

No new governance protocol, persistence schema, cryptographic key management or external security dependency is added by the freeze.

## Managed MongoDB credential wiring

The evaluation freeze also closes the managed-client deployment gap exposed by authenticated MongoDB. When the host sets `MANGOME_MONGODB_URI_FILE`, managed Claude/Codex configuration now carries the credential-file path into the MangoMe MCP process together with the non-secret trust-boundary posture (`MANGOME_TRUST_BOUNDARY`, expected service uid, least-privilege enforcement and explicit remote-Mongo opt-in).

The MongoDB URI itself is never copied into managed client configuration. If only `MANGOME_MONGODB_URI` is present, attestation reports `MONGODB_URI_NOT_PERSISTED_USE_CREDENTIAL_FILE`. If neither a managed credential file nor a process URI is available, attestation reports the warning `MONGODB_CREDENTIAL_SOURCE_MISSING`. These are sanitized deployment diagnostics; no URI, username, password or credential-file contents are returned.

For the evaluation host this fixes the configuration path that previously fell back to unauthenticated `mongodb://127.0.0.1:27017`. A production trust boundary still requires MangoMe to run under a service identity that untrusted workers cannot use to read the credential file directly.

## Zero-touch credential adoption

Managed setup now resolves MongoDB authority before it rewrites Claude/Codex bindings. It can reuse an existing `MANGOME_MONGODB_URI_FILE`, normalize a process-only URI into an owner-only file, recover credential metadata from current or `.mangome.bak` MangoMe client bindings, and recover the environment of a still-live legacy MangoMe MCP process. Secret URI values are never returned in setup/attestation output.

Every discovered credential is tested against the requested canonical database using the same `ensure_indexes()` capability required by MangoMe runtime. Only a source that can initialize/read the canonical database is adopted. Once adopted, the secret is written to `~/.config/mangome/mongodb-uri` with owner-only permissions, the direct URI is removed from the setup process environment, and managed client configuration receives only `MANGOME_MONGODB_URI_FILE`.

If MongoDB requires authentication and no discovered credential has authority on the canonical database, setup stops once with `BOOTSTRAP_AUTHORITY_REQUIRED`. It does not invent a password, silently reuse `mangome_uai_eval`, write a broken binding, or ask an agent to reconstruct database authority from project state. An already-running host/agent process may still need to reload its MCP registry after its stale binding is replaced; MangoMe reports `session_reload_required` when setup removed a stale MangoMe alias.
## Zero-touch bootstrap authority

The evaluation freeze makes the CPM/1 installation boundary explicit so the installer cannot deadlock itself. An explicit MangoMe install/update/repair request authorizes the normal `mangome setup` path to adopt an already-existing MongoDB credential source, bind the canonical `mangome` database, and run idempotent `ensure_indexes()` for the indexes declared by the installed release. This bounded operation is deployment bootstrap, not a WorkIdentity, self-approval, registered schema migration, or canonical domain mutation.

The exception is deliberately narrow. Setup must not create or alter MongoDB users/roles, run registered schema migrations, rewrite canonical domain documents, repair business data, or change database identity. Those still stop with `DATABASE_CHANGE_REQUIRED`; an authentication-protected MongoDB with no reusable authority stops with `BOOTSTRAP_AUTHORITY_REQUIRED`.
## Managed runtime zero-touch closure

The final evaluation freeze removes the hidden prerequisite that an operator or agent must run `mangome setup` before the managed MCP runtime can use MongoDB. On first canonical database access, a managed runtime now executes the same bounded zero-touch adoption/bootstrap path automatically. This applies to HEALTH and productive calls because both converge on the central runtime service factory.

Bootstrap is attempted at most once per MCP process. Success or failure is cached so a missing credential cannot trigger repeated process/config scans and repeated MongoDB connection timeouts on every tool call. HEALTH exposes only sanitized `database_bootstrap` state and stable reason codes. After an operator repairs a failed authority source, the MCP process must be restarted rather than entering an uncontrolled retry loop.

The trust-boundary snapshot is evaluated after zero-touch has had a chance to adopt a credential, avoiding mixed reports in which `database_ready=true` is paired with stale pre-bootstrap credential metadata.

The semantic worker facade also preserves stable operability reason codes and separates argument-binding errors from `TypeError` raised inside an already-bound capability. Error-shaped results are treated as blocked even when the underlying capability omitted an explicit `ok=false`.

CPM/1 now distinguishes deployment bootstrap from canonical data/schema mutation. Credential adoption, canonical database binding and idempotent declared-index creation are allowed installation plumbing. MongoDB user/role management, registered MangoMe migrations, canonical domain rewrites, business-data repair and database-identity changes remain outside that authority.

Credential discovery prioritizes an already-live legacy MangoMe MCP process before stale client configuration backups. This matters for historical releases that inherited a MongoDB credential into the MCP process without persisting that secret in Codex/Claude configuration.
